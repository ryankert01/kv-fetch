Qwen3.5 瓶頸夜巡

昨晚 profiling harness 在 vLLM 上輪流跑 Qwen3.5-4B（24 層 GDN + 8 層 attention 的混合模型）和同尺寸的 dense 模型 Qwen3-4B，目標是找出混合模型專屬、值得拿來修的瓶頸。以下是每個候選的證據、是否合格，以及要不要開始修。

結論

三個瓶頸是真的、而且混合模型專屬，但都沒通過規則 (c)。兩個上游已經有 PR 在修；第三個是飽和時的「搶占乒乓」，影響最大，可是現成的 --watermark 0.1 就能拿回大半。Speculative decoding 在 hybrid 上反而比 dense 好用，沒看到專屬的驗證瓶頸。

這個乒乓是今晚最清楚的機制：預設設定下，c=256 的推理負載重算了 5.1M 個 token，比全部 decode 出來的 token 還多，含重算的 step 佔了 26% 的時間。

建議：不要從這幾個裡挑一個當論文開始修。先花半天把乒乓寫成上游 issue（資料都有了）；論文題目往上游還沒在做的層級找，下一晚的 harness 先量更大的 hybrid。見最後一節。

規則：(a) 佔 step 時間 ≥ 15%；(b) 是純 overhead，或端到端 ≥ 10%；(c) 上游還沒修、也沒有現成開關能消掉。

候選 1 · f8 / f9 / f10

飽和時的搶占乒乓

推理型負載：輸入 1024、輸出 8192 token，長度各在 ±50% 內均勻分布；vllm serve 預設的 2048-token 預算、256 個 seq。c=64 時一切正常；到 c=256，KV cache 滿了，吞吐量就塌下去。

同樣大約 133 個 running request、同樣多的 engine step，prefix caching 開著（hybrid 會進 align mode）比關掉多搶占 4.3 倍，每個 step 慢 27%，輸出少 22%。

機制：把 scheduler 包起來看（f10，離線重現）

把同樣的負載搬到 in-process 的 LLMEngine，攔下每一次 schedule、allocate_slots 和搶占。它重現了 server 的數字：搶占 3484 次（server 是 3474），1480 tok/s（server 是 1576）。

  1. 搶占是 LIFO：被踢的是 running[-1]，也就是最晚進來的 request。被踢的 request 回到佇列最前面。
  2. 接納時只檢查「整條序列放得下」，但什麼都沒預留。剛被接回來的 request 開始重算，每個 1584-token chunk 要 3 個新 block（align mode 把 chunk 對齊到 528）。
  3. 同時約 115 個 decode 中的 request 每跨過一個 528-token 邊界就要新 block：align mode 下是 4 個（attention 1 個，加上 3 個 Mamba group 各一個 state block）。
  4. 大約兩個 step 之內，總有一個 chunk 或邊界要不到 block。這時被踢的又是最新的那個，也就是剛接回來的 request。它的重算白做了，下一輪又被接回來。

為什麼 watermark 有用：它讓接納等到有 194 個 block 空著才放行，足夠把重算做完，乒乓就停了（搶占剩 128 次）。關掉 prefix caching 也有幫助但比較少：chunk 變回 2048、跨邊界只要 1 個 block，失敗的窗口比較窄（800 次）。

為什麼不算合格：現成開關就能把吞吐量從 1576 拉到 2128 tok/s、TPOT 從 92 降到 62 ms，不增加 TTFT。剩下的是一個設定上的發現（hybrid 在預設 watermark 0 下飽和時會掉 26%），適合開 issue，不夠撐一篇論文。上游 #62752 / #62878（open）處理的正是 align mode 跨邊界的 block 帳，但只在 CPU 上重現、範圍是 speculative decoding，沒有 serving 數字。

Dense 對照：Qwen3-4B 在同等記憶體壓力下（80 個 in flight，running 約佔 44%，和 hybrid 的 45% 相當）也會搶占，但不會乒乓。被接回的 request 會先把重算做完，中位數再 decode 106 個 step 才又被選中；hybrid 是 2 個 step。dense 的 victim 幾乎從不是重算到一半的 request（424 次裡 2 次），hybrid 是 3484 次裡 2045 次。差別在 block 的粒度：dense 一個 block 16 token、跨邊界要 1 個；hybrid 一個 block 528 token、跨邊界要 4 個，配置失敗時通常還剩 2 個空 block。

Prefix caching 本身不是問題：dense 開或關 prefix caching 幾乎一樣（搶占 424 對 423 次、751 對 740 tok/s）。hybrid 開著會多 4.3 倍搶占、少 22% 輸出，是因為它把 hybrid 帶進 align mode。hybrid 關掉 prefix caching 的離線 trace 也對得上：搶占 779 次、接回後中位數 44 個 step 才又被選中、每個輸出 token 只重算 0.41 個，行為和 dense 一樣。

候選 3 · scan / nsys

短 step 的固定下限

Hybrid 做一個短 prefill，256 token 以內固定要 24 ms 左右，dense 只要 12 ms。nsys 顯示 512-token prefill 的 GPU 只忙 41%：GDN 的 chunk 路徑每層在 CUDA graph 外 launch 約 17 個 kernel，加起來約 400 個。瓶頸在 launch，不在 GDN 的運算。

狀態：在多輪對話的 serving 測試裡（64 個共用的 4K prefix），hybrid 反而每項都贏 dense（輸出 1.3–1.9 倍），決定性的是容量，不是這個下限。上游 #61779 和 #61952（open）把 GDN 核心放進可中斷的 CUDA graph，A100 上 mixed step 的 host 時間從 99 降到 55 ms。

已排除

Decode 沒有空間

8K context、batch 1–64 的 decode step，整個 step 達到記憶體頻寬上限的 0.89–0.95，GPU 忙碌 99–100%，GEMM（含 lm_head）是 weight-read 上限的 0.78–0.96。沒有 overhead 可以拿。

新方向 · f11

Speculative decoding（初探）

Qwen3.5-4B 用自帶的 MTP 層，Qwen3-4B 用社群的 EAGLE3 head；k = 0–3 個 draft token，batch 1 / 16 / 64，每個 request 輸出 1024 個 token，prompt 是 AIME 題目。要看的是：驗證 k 個 draft token 時，經過 GDN 層的成本會不會比經過 attention 層漲得快。

Step 成本：batch 1 時，hybrid 每多一個 draft token，step 多 2.1–2.7 ms，dense 只多 0.6–0.9 ms。大部分是 drafter 的成本，不是 GDN 驗證：MTP 每個 draft step 跑一整層 decoder 加上 248K 詞表的 lm_head（batch 1 時一次 1.36 ms），EAGLE3 只有一層、draft 詞表 32K。到 batch 64 兩邊多出來的成本差不多大，驗證 64 ×（k + 1）個 token 本來就是 compute-bound。

狀態：這個解析度下看不到 hybrid 專屬的驗證瓶頸；要把 MTP 層和 GDN 驗證拆開，得再跑 kernel trace。上游在 GDN 的 state 這邊已經有 RecoverSSM（#58863）、ReplaySSM 加 prefix caching（#56466）等 PR；drafter 這邊的 sparse LM head 是 #59740。

下一步

要不要開始修？

不要從這五個裡挑一個當論文開始修。三個 hybrid 專屬的瓶頸都是真的，但上游在過去兩到四週都已經動手（PR 已 merge 或還 open），或者有現成開關；speculative decoding 在 hybrid 上比 dense 好用。

今晚最明確的結論是：vLLM 的 hybrid 路徑正在被密集地修。在「4B 模型、單卡、單一 engine 瓶頸」這個層級，論文的窗口很小：我們修好一個，上游幾週內大概也會有。

  1. 半天、確定能做的：把乒乓寫成上游 issue。離線重現（thrash_trace.py）、server 數字、dense 對照、觸發原因的分布都有了。可以附一個小 PR：victim 不要選正在重算的 request，或替 hybrid 設非零的預設 watermark。這不是論文，但能建立 credibility，也能看維護者怎麼回。
  2. 論文題目：往上游還沒在做的層級找。下一晚的 harness 先排更大的 hybrid：Qwen3.6-35B-A3B（MoE，FP8）、Qwen3.5-27B-FP8、9B，以及 TP=2。MoE kernel 和 GDN 的交互、多卡下的 state，今晚完全沒量。佇列裡已經有 9B 的 base 和 ablation job 在等。
  3. 要先用一晚檢驗的假設：hybrid 的搶占用換出取代重算。hybrid 的 state 大小固定，換到 host 估計比重算便宜約 50 倍，dense 約 13 倍；V1 只會重算，上游兩次 preempt-offload 的嘗試都沒 merge。可是 watermark 0.1 已經把飽和時的搶占壓到 128 次，所以得先找出搶占在調好的設定下還是很多的負載（長輸出、突發流量），差距夠大才值得做。

Harness 本身

一個 JSON job 佇列（pending / running / done / failed），每個 job 自己一個 process group，逾時整組砍掉；每做完一個 job 就重算 findings。GPU 規則：永遠不用 GPU 0，只用 Ada 卡 4–6；GPU 0 有人用時同時只跑一個 job。

程式：scripts/profile/harness.py、serve_bench.py、serve_timeline.py、thrash_trace.py、thrash_report.py、spec_profile.py。完整紀錄在 results/profile/NOTEBOOK.md（branch phase0）。
