RL rollout 兩道關卡

昨天說好的計畫：先跑 R1，沒過就跑 R2，兩個都沒過就放棄 RL rollout 這個方向。兩個都沒過。這篇說明每個實驗問什麼、怎麼量、數字怎麼看，最後列出接下來可以選的路。

結論

R1（更好的搶占／admission 策略）：沒過。Hybrid 在最好的 watermark 設定下，離「知道所有長度的完美排程」只差 6.4–6.8%，門檻是 15%。真正的損失來自 vLLM 的預設值 --watermark 0：hybrid 因此慢 26–37%，調成 0.05 就幾乎全部回來。這是一個現成的開關，不是新方法。

R2（換權重後沿用舊的 recurrent state）：沒過。跑了 32 個真的 GRPO step 之後，沿用舊 cache 造成的 KL 最多只有 bf16 數值雜訊（floor）的 1.74 倍，門檻是 3 倍。扣掉雜訊後只佔 policy 本身變化的 12–16%，dense 模型是 6–18%，兩者分不出差別。

所以：照計畫，RL rollout 這個方向放棄。下一個方向要你決定，選項在最後一節。

兩個門檻都在跑之前寫進 EXPERIMENTS.md；中途的兩次修改（R1 加同長度對照、R2 改成 128 題與 32 步）也都在看到任何結果之前。

R1 · 2026-10-29

R1：更聰明的搶占能省多少？

問題。RL 的一個 rollout step 一次丟出幾百個長回答。這裡是 64 題 MATH-500（level 3–5）、每題 8 個 sample、上限 16K token，共 512 個 request。記憶體不夠時 vLLM 會把 request 踢出去（搶占），之後回來再重算。如果有一個知道每個回答長度的完美排程，能比 vLLM 快多少？差很多，才值得設計新的 admission／搶占策略。

方法。先讓兩個模型各自真的回答一次，記下每個回答的長度：hybrid 是 Qwen3.5-4B（24 層 GDN + 8 層 attention），dense 是 Qwen3-4B。再把 512 個 request 一次丟給 vLLM 0.32，強制每個都生成到原本的長度，記錄每個 scheduler step。用這些 step 擬合時間模型：固定成本，加上每個 decode、每個 context token、每個 prefill／重算 token 的成本。再算同樣記憶體下最少要幾個 step（完美裝箱、完全不重算）。headroom = 1 − 下限 ÷ 實際時間，是任何策略能贏的上限。

門檻（事先定好）。Hybrid 最好的設定在記憶體比例 0.5 和 0.7 下都離下限 15% 以內，就放棄。

同長度對照。Hybrid 的回答平均長了將近一倍（11,187 vs 5,923 token，46% vs 5% 撞到上限），所以門檻的第二個條件（hybrid 的 headroom 是否比 dense 大）改成讓 hybrid 照 dense 的長度生成，再跟 dense 比。第一個條件已經判了，這張表只是補齊紀錄；之後如果要開 upstream issue，用的就是這組證據。

同樣的長度，同樣的結論。預設值的損失還是只出現在 hybrid：watermark 從 0 調到 0.05，hybrid 的時間縮短 22–26%，dense 只有 1.5–4.1%。調過以後 hybrid 離下限 6.7–9.1%，dense 4.0–6.3%；第二個條件差 1–3 個百分點，但都在 15% 以內，而第一個條件已經判了。Hybrid 剩下的差距主要是 step 數（完美裝箱的 1.18–1.41 倍，dense 1.05–1.16 倍），不是重算。

附帶一個數字：同樣的回答長度、同樣的記憶體比例，調過的 hybrid 跑完一個 rollout step 要 1,293–1,542 秒，dense 要 3,215–3,883 秒。Hybrid 的記憶體池裝得下約 3 倍的 token。

R2 · 2026-10-29 → 30

R2：換了權重，舊的 state 還能用嗎？

問題。非同步 RL 會在回答生成到一半時換上新權重。PipelineRL 和 Magistral 沿用舊權重算出的 KV cache 繼續生成，AReaL 選擇重算，Kimi K3 每輪清空 hybrid 的 state pool。Dense 模型的舊 KV 是每個 token 各自的向量；hybrid 的 recurrent state 卻把整段歷史壓成一個固定大小的矩陣。如果舊權重寫進 state 的誤差比舊 KV 大很多，「怎麼便宜地修好 hybrid 的舊 state」就是 hybrid 專屬的題目。

方法。從釋出的權重開始跑真的 GRPO：128 題 MATH、每題 8 個 sample，只用有對有錯的題組，DAPO 的 clip（0.2 / 0.28），AdamW lr 1e-6，fp32 master 放 CPU、bf16 放 GPU。第 1、2、4、8、16、32 步之後，拿 32 個舊權重生成的長推理回答，在第 1K、4K、8K token 切開，接下來 1,024 個 token 用 teacher forcing，比較下面幾種 cache 的下一個 token 分佈：

  • F：新權重，新權重算的 cache。換權重後重算，當作標準答案。
  • S：新權重，舊權重算的 cache。全部沿用。
  • P：舊權重，舊 cache。等於還在用舊 policy。
  • floor：新權重一次跑完整段。權重一樣，只是 kernel 路徑不同，代表 bf16 的數值雜訊。
  • Hybrid 另外拆成 S_state（只有 linear-attention 的 state 是舊的）和 S_kv（只有 attention KV 是舊的）。

門檻（事先定好）。Hybrid 要在某個 step 和 cut 上，KL(F‖S) 至少是 floor 的 3 倍，而且 ρ = KL(F‖S) ÷ KL(F‖P) ≥ 1，或 ≥ max(0.5, 3 × dense 的 ρ)，才算活著。

第 32 步，KL 扣掉 floor，單位 1e-4；每格是 12 個 probe 的平均（dense 8K 是 7 個）。

三個觀察。

  • 舊的 recurrent state 不是主要來源。只換 state 和只換 KV 的誤差差不多大（0.5–1.1 vs 0.7–1.2），兩者相加是全部沿用的 70–100%。
  • 誤差在切點後最大，之後變小。Hybrid 切點後前 64 個 token 是 floor 的 2.2–2.5 倍，第 257–1,024 個 token 降到 1.5–1.7 倍。新 token 不斷寫進 state，舊權重留下的部分被 gate 慢慢衰減，不會累積。
  • 同樣的 policy 變化下也分不出來。同步數下 hybrid 的 policy 變得比 dense 多（P 超出雜訊 1.4–1.6e-3 vs 0.7e-3）。比 policy 變化差不多的點，hybrid 第 16 步 vs dense 第 32 步，S / floor 是 1.24–1.32 vs 1.06–1.27。

沿用舊 state 跟沿用舊 KV 一樣可以接受。PipelineRL 已經這樣做，這是工程上的預設，不是論文題目。

方法上的教訓

兩個差點讓結果算錯的地方

  • Async scheduling 差一步。vLLM 0.32 預設非同步排程，每個 step 記到的時間其實是上一個 step 的 GPU 工作。逐步擬合的 R² 只有 0.05，重算成本被估成 14 µs/token。改成 50 個 step 的視窗加總以後 R² 是 0.90–1.00，重算約 97 µs/token；dense 的 headroom 從 1.7% 修正為 7.5%。
  • bf16 的解析度。小 lr 的單步更新多半寫不進 bf16 權重，所以 staleness 實驗只看 1–8 步會得到「全部等於雜訊」。這也是門檻要求「至少 3 倍 floor」、並把步數延長到 32 的原因。
下一步

要你決定的事

連續三個方向（hybrid 的 prefix caching、vLLM profiling 找瓶頸、RL rollout），看到的差距都已經被現成的開關或上游正在做的 PR 補上。vLLM 對 hybrid 已經調得相當好，從 profiling 找題目的效率很低。可以選的路：

  1. 開 vLLM upstream issue（小，跟論文無關）。Hybrid 在 RL rollout 這種一次大量長回答的負載下，預設的 watermark 0 讓一個 step 慢 26–37%，調成 0.05 就把時間縮短 21–29%；dense 在預設值下只差 1–4%。資料已經齊了，要你同意才會發。
  2. 回到唯一過關的結果 H3。Hybrid attention 層的 page 選擇在 512 budget 下比 Quest 多 10.8 分（CI 4.2–18.3）。模擬審稿的主要問題（題目只有 30 題、confirm split 還沒跑、baseline 只有 Quest）都屬於評估範圍。第一步是跑事先保留的 confirm split，一個晚上就知道效果是不是真的。弱點是方法跟 ShadowKV／InfLLM 很像，沒有 hybrid 專屬的部分。
  3. 換一種找題目的方式。不從 profiling 找瓶頸，改從 hybrid 做不好的地方出發。例如 H-a 看到 hybrid 的 attention 層比 dense 更分散（oracle@512 漏掉 22.7% vs 11.6%），可以從長 context 檢索的準確度找題目。

我的建議：1 跟其他選項不衝突，可以先做。論文的部分我選 2：它是唯一有效果通過門檻的結果，confirm split 一個晚上就能判斷值不值得繼續。如果 confirm split 沒過，再考慮 3。
