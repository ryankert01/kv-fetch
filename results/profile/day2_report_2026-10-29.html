Qwen3.5 放大巡檢

昨晚只量了 4B。今天同一套 harness 往上量 Qwen3.5-9B、Qwen3.5-27B-FP8 和 Qwen3.6-35B-A3B-FP8（MoE），各配一個同尺寸的 dense 模型：engine profile、kernel trace、一般負載下的 serving。問題還是一樣：有沒有混合模型專屬、值得拿來寫論文修的瓶頸。

結論

模型放大以後沒有冒出新的 kernel 瓶頸。GDN 在各尺寸只佔 step 時間的 1–16%，其餘是 GEMM、MoE 和 attention。Serving 在一般負載下 hybrid 全面贏 dense（1.16–2.5 倍），贏在記憶體池能裝的 token 多。

隨模型變嚴重的只有一件事：block 變大。vLLM 讓每個 block 和一個 state 一樣大，所以 block 從 4B 的 528 token 長到 27B 的 784、MoE 的 1056；fp8 KV 也會讓它翻倍。block 越大，align 切段、cache 命中後的重算、配置粒度（昨晚的搶占乒乓）都跟著變大。MoE 和 27B 在 c=64 就已經乒乓：vLLM 的預設設定讓它們少了 9–22% 的吞吐量，dense 模型不受影響。

但這些成本每一項上游兩週內都有 PR 在處理，最後一節逐項列出來。照規則 (c)，今天也沒有合格的候選。

規則：(a) 佔 step 時間 ≥ 15%；(b) 是純 overhead，或端到端 ≥ 10%；(c) 上游還沒修、也沒有現成開關能消掉。

模型與記憶體池

量了哪些模型

FP8 checkpoint 在 Ada 上沒有原生 FP8 運算，vLLM 改走 Marlin 的 weight-only 路徑；hybrid 和 dense 都一樣，所以比較仍然公平。FP8 模型用 0.92 的 GPU 記憶體，其他用 0.85。

「放得下的 request」：每個 request 要 ⌈context / block⌉ 個 attention block 加 3 個 state block（每個 Mamba group 一個）。state 佔池 = 2K context 時 3 個 state block 佔該 request 的比例。27B 沒有同尺寸的 dense FP8 checkpoint，只量了 hybrid。

Engine · f1

MoE 的短 prefill：還是 align 切段加固定下限

狀態：和昨晚同一個問題，block 翻倍所以更明顯。上游 #60659（FLA 後端，open）和 #63670（draft，直接拿掉切段）；短 step 下限是 #61779 / #61952。

共同原因

block 跟著 state 變大

vLLM 的 hybrid KV 池只有一種 page 大小：attention 的 block 要調到一頁至少放得下一個 Mamba group 的 state。state 越大、或 attention 每個 token 越省，block 就越長。

block 變大會讓三件事一起變差：

  1. Align 切段：prefill chunk 要切在 block 邊界上。batch 1 是多一個 step（上一節）；serving 時 token 預算扣掉 decode 之後還要往下取整到 block 的倍數，1056-token block 下一個 step 最多只能做 1056 個 prefill token，剩下的預算閒著。
  2. Cache 命中後的重算：state 只存在 block 邊界，命中最多要重算將近一個 block。27B 的 cache-hit 重算 step 是 195 ms，bf16 state（block 400）是 99 ms。
  3. 配置粒度：decode 每跨一個邊界要 4 個 block（1 個 attention、3 個 state），池子是以很粗的單位用完的，昨晚的搶占乒乓就是這樣來的。下一節在一般負載下又看到它。

fp8 KV 的例子最直接：4B 開 fp8 KV，token 容量從 986K 變成 1.95M，可是 block 數幾乎沒變（1868 → 1847）。2K 的 request 從 7 個 block 變 5 個，只多放 38% 的 request；dense 模型會是 2 倍。

Serving · P4

一般負載下 hybrid 贏在容量

vllm serve 預設設定（2048-token 預算、256 個 seq），random prompt、ignore_eos。reasoning_var：輸入 1024、輸出 8192，長度各 ±50%；chat：輸入 4096、輸出 512。每種設定各跑 c=16 和 c=64。

27B：池只有 199K token，c=64 時同時只跑得動約 25 個 request。預設設定搶占 1006 次（每個 request 7.9 次），TPOT p99 290 ms；watermark 0.1 壓到 46 次，輸出 346 → 443 tok/s（+28%），TPOT 中位數 83 → 57 ms。TTFT 中位數兩邊都在 560–580 秒，是排隊。這裡沒有同尺寸的 dense FP8 checkpoint 可以對照。

量測上的兩個修正：(1) 原本所有 bench 都用 seed 0，random dataset 的前 64 個 prompt 在 c=16 和 c=64 一模一樣，9B hybrid 的大池子還留著上一輪的 prompt，chat c=64 有 23% 的 prefill 是免費的。換新 server 重跑後是 1.42 倍，不是 1.72 倍；現在每個（workload, c）各用自己的 seed。(2) GPU 0 空出來、harness 改成三張卡並行時，所有 serving job 都用 port 8765，兩個 job 打到了 MoE 的 server。已改成每張卡各自找空的 port，受影響的 run 都重跑或標成無效。

Decode · probe / ablation

State 每步寫回：比估計的小

GDN decode 每一步都把整個 fp32 state 讀進來再寫回去。我原本用位元組估計，2K × 128 時這佔 decode 搬移量的 40% 左右；kernel trace 在 8K × 64 量到的只有 16%。

狀態：上游 #62004（open，Dao AI Lab 和 NVIDIA）把 ReplaySSM 做到 GDN 的一般 decode：用一個小 ring buffer 記最近的輸入，每 L 步才寫回一次 state；Mamba2 的版本已經 merge。能省的最多是這 16% 裡寫回的那一半。
